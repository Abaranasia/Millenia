# Formant-Preserving Pitch Shifter — Research Notes

**Purpose**: a new diagnostic (`PitchShifterTests.cpp`, "output frequency error across a range of INPUT frequencies at the default +12st shift") measured ≤0.011% pitch-tracking error across a 110Hz–3520Hz sine sweep, ruling out a pitch-tracking bug behind the "sounds chipmunk on higher notes" complaint. `PitchShifter` is a WSOLA-style time-domain grain shifter with no formant compensation — it shifts the whole spectral envelope by the same ratio as the pitch (the textbook "helium voice"/Mickey Mouse effect), which is most audible on higher, harmonically distinct content. This document researches whether, and how, a formant-preserving redesign could work given this project's single hardest constraint: the shifter runs *inside* `DattorroTank`'s recirculating cross-feed (`ShimmerReverbEngine::process()`: `shiftedFeedback = shifter.processSample(tank.peekFeedbackSignal())`, fed back via `tank.processSample(input, safeFeedback)`), not as a one-shot effect on a track. It builds directly on `docs/fdn-shimmer-reverb-research.md`'s already-verified findings about this loop's stability tensions (§3 there in particular) and on this project's own Freeze investigation history (`docs/shimmer-reverb-implementation-plan.md`'s Phase 9 section).

**Scope note on verification**: same discipline as the FDN research doc — every citation checked via search and, where possible, fetched directly; secondary paraphrases (search-engine summaries of pages this research could not directly fetch/quote) are labeled as such, distinct from directly-quoted primary sources.

## 1. Formant-preserving pitch-shifting technique survey

Three established technique families were found, plus their practical open-source implementations:

### 1a. PSOLA (Pitch-Synchronous OverLap-Add) and TDHS (Time-Domain Harmonic Scaling)

**Mechanism**: instead of windowing at a fixed grain length (as Millenia's `PitchShifter` does — 20ms regardless of input pitch), PSOLA detects "pitch marks" (glottal closure instants / period boundaries) in the input and windows exactly **one pitch period** around each mark. Because the analysis window is locked to the input's own natural period, the extracted grain already carries that period's actual formant/resonance content; overlap-adding those pitch-synchronous grains at a *new* target period changes the fundamental frequency while leaving the spectral envelope (formants) essentially where they were. This is the oldest, most literature-verified formant-preserving family: **Lent, "An Efficient Method for Pitch Shifting Digitally Sampled Sounds," Computer Music Journal 13(4), 1989** (confirmed via search/citation trail — this is the canonical TDHS reference) windows sections one period long and recombines them at the new period; a Computer Music Journal course-page summary (John Lazzaro, UC Berkeley, "Music 209 Week 5," found via search, not independently fetched) confirms this is analytically understood as approximating frequency-domain spectral-envelope interpolation while staying entirely in the time domain. Search results also describe PSOLA generically as having "very low computational cost" and being usable for "pitch-shifting, formant-shifting, pitch correction, and chorus effects on voice and monophonic signals" (emphasis on *monophonic* — see §2).

### 1b. Phase vocoder + cepstral or LPC spectral-envelope separation/reapplication

**Mechanism** (the "source-filter" approach): decompose the signal into an excitation (fine harmonic/pitch structure) and a spectral envelope (formants), pitch-shift only the excitation, then reimpose the *original* envelope on the shifted result. Two established ways to extract the envelope, per a search-engine summary of spectral-envelope-estimation literature (not independently fetched as a single paper, but consistent across multiple sources): **LP-based** (linear prediction / LPC, modeling the envelope as an all-pole filter) and **cepstral-smoothing-based** (discrete cepstrum, "true envelope" — reported as sonically superior to discrete cepstrum but more expensive). Stephan Bernsee's own writing (`blogs.zynaptiq.com/bernsee/formants-pitch-shifting/`, fetched directly — **primary source**) states the mechanism plainly: naive FFT pitch shifting "expand[s] the fundamental frequency along with all harmonics and the spectral envelope," and "keeping the spectral envelope, i.e. the position of the formants... yields a natural sounding transpose." His companion article on FFT-based pitch shifting (`blogs.zynaptiq.com/bernsee/pitch-shifting-using-the-ft/`, fetched directly — **primary source**) gives concrete, load-bearing numbers for §4 below: **FFT frame sizes of 1024–4096 samples** (1024 "generally fine for speech," 2048 "works well with music") with **75% overlap (4x oversampling)** recommended for reliable frequency tracking, and an explicit **algorithmic I/O latency** ("`inFifoLatency` samples... the start of your output will contain that many samples of silence") inherent to the block-based FIFO structure. Neither Bernsee article discusses feedback-loop or recirculating use.

Real, verified open-source implementations of this family:
- **`jurihock/stftPitchShift`** (GitHub, README fetched directly) — STFT-based, explicitly built "inspired by Stephan M. Bernsee's smbPitchShift.cpp," with a dedicated `Cepster` module implementing cepstral-domain envelope estimation via liftering (a "quefrency" cutoff parameter in milliseconds controls how much spectral detail is treated as envelope vs. excitation). Default **1024-sample FFT window at 32x overlap**. MIT-licensed, C++ and Python. This is the most directly relevant, purpose-built, verifiable open-source reference found.
- **Signalsmith Audio's `signalsmith-stretch`** (GitHub, README fetched directly) — from the same author already cited in this project's own docs (Geraint Luff, ADC22 "Four Ways To Write A Pitch-Shifter" talk, already referenced in `shimmer-reverb-concepts.md`). FFT/block-based; ships an optional `compensatePitch` formant-correction flag, but the README itself states this correction "is not as sharp as monophonic algorithms (such as PSOLA)" and needs a fundamental-frequency estimate — i.e. even a modern, actively-maintained library concedes formant correction degrades without reliable pitch tracking (reinforcing §2's core caveat below). Reports latency via explicit `inputLatency()`/`outputLatency()` accessors; documentation is framed around bounded/one-shot stream processing (`.seek()`/`.flush()`), not continuous feedback-loop use. MIT-licensed.
- **RubberBand** and **SoundTouch** — both real, mature, open-source time/pitch-stretch libraries (confirmed via search); RubberBand is dual-licensed (GPL or commercial), SoundTouch is more permissively licensed but is described in search results as handling transients (percussive material) poorly. Neither was independently verified here to have a dedicated formant-preservation mode as strong as `stftPitchShift`'s.
- **Classic reference**: Stephan Bernsee's `smbPitchShift.cpp` (found via search, multiple mirrors including an MIT source-tree copy) is the widely-ported baseline FFT phase-vocoder pitch shifter that most of the above descend from or compare against; it does not include formant preservation itself (that's what `stftPitchShift` and others add on top).

### 1c. Full source-filter vocoders (STRAIGHT, WORLD)

**Mechanism**: decompose speech into F0 (fundamental), aperiodicity, and spectral envelope, and resynthesize after modifying only F0 — a heavier, more speech-specific relative of 1b. Per search results (multiple sources, consistent): **WORLD** (Morise et al.) is reported as "significantly preferable" to the older **STRAIGHT** (Kawahara et al.) vocoder for speech resynthesis and as reducing computational cost without quality loss. Both are designed for **speech-specific, offline or quasi-real-time analysis-resynthesis**, not for wide-bandwidth musical/reverberant signals recirculating at audio-loop rates; no evidence was found of either being used inside a real-time feedback loop, and their design assumptions (harmonic+aperiodicity speech model) make them a poor conceptual fit for this project's actual signal (a diffuse reverb tail, not a voice). Listed for completeness, not recommended further.

### 1d. Practical, forum-level real-time techniques

The KVR Audio DSP forum thread "Formant preserving pitch shifting in realtime" (fetched directly) was thin on technique detail (a "<25ms latency, 1024-sample detection window" pitch shifter was mentioned, but no LPC/cepstral discussion). The katjaas.nl "low latency pitch shifting" page (fetched directly, a well-known DIY-DSP reference) is candid and useful as a *negative* data point: its author explicitly ships a "few-millisecond-latency" time-domain delay-line pitch shifter and states plainly, **"No formant preservation, but fast response"** — i.e. a knowledgeable practitioner deliberately traded away formant preservation specifically to keep latency near-zero, the same trade-off Millenia's current `PitchShifter` makes. This independently corroborates §4's central finding: low latency and formant preservation are treated in the practitioner literature as being in real tension, not a solved-for-free combination.

## 2. The hard constraint: recirculating, not one-shot

Every technique in §1 was designed and evaluated for a **one-shot pass over a track** (a voice, an instrument, a mix) — analyze once, correct once, done. Millenia's shifter does not get that luxury: its output is fed back into `DattorroTank`'s cross-feed every sample, and — per this project's own Phase 8 finding, already documented in `docs/fdn-shimmer-reverb-research.md` — **`tankOut` (what the ear actually hears as "the shimmer") is dominated by content that has already recirculated and diffused through the tank multiple times**, not by a single clean pass. Two consequences follow that no source found here addresses directly, because no source found here builds a formant-preserving shifter for this use case:

- **PSOLA/TDHS's core assumption — a well-defined, trackable pitch period — degrades exactly where this project's signal lives.** PSOLA explicitly targets "voice and monophonic signals" (§1a); Millenia's shifter processes a mono-summed but potentially polyphonic/chordal input, further diffused by four cascaded allpass stages before it even reaches the shifter (`DattorroTank::peekFeedbackSignal()` reads branch B's output, already passed through allpass→delay→damping→allpass→delay). A pitch/period detector run on that signal has no single period to lock onto for a chord, and even less for later-generation, more-diffused recirculating content. This is not a hypothetical risk: this project already spent Phases 3 and 7 painstakingly eliminating phase-incoherence and metallic-sideband bugs from its current *non*-pitch-synchronous grain design; a pitch-synchronous redesign reintroduces a new, likely-worse failure mode (mistracked/wrong-period grains) on precisely the signal this reverb is built to process.
- **Cascading recirculation is in direct tension with "preserve the *original* envelope."** Each lap through the loop re-shifts already-shifted content (per `docs/fdn-shimmer-reverb-research.md`'s own account of Phase 8's "geometric pitch compounding" bug and its `shimmerWeight`/`plainWeight` fix): generation 1 is +12st from the dry input, generation 2 (a reshift of generation 1, budget-limited by the crossfade) trends toward +24st, etc. If formant correction naively reimposes the *original dry input's* envelope on every generation regardless of how many octaves up the pitch has already cascaded, by the second or third generation the reimposed formants would sit unnaturally low relative to a fundamental that's climbed several octaves away from them — a known failure mode of "over-preserved" formants at large shift ratios (this follows directly from how formant shifters are described to behave at extreme ratios in the sources above, e.g. Signalsmith's own concession that formant correction needs an F0 estimate and is inherently less "sharp" than a one-shot monophonic case; it is this document's own reasoning, not a directly-cited finding, since no source addresses a *cascading* formant-preservation case specifically — flagged as such). The practical fix — track and reimpose the envelope of whatever is *currently* re-entering the shifter each pass, rather than a frozen original snapshot — is a natural extension of the same technique (a continuously-updated, "leaky" formant correction, conceptually similar to a vocoder's continuously-tracked modulator envelope) but is, as far as this research found, not something any cited source builds or tests; it is a reasoned proposal, not a verified one.
- **A silver lining**: the "chipmunk" complaint is very likely most audible on the first one or two generations (closest to the identifiable dry input); by the third-plus generation, Dattorro's own diffusion has already smeared the signal into something less tonal, where the perceptual value of exact formant fidelity drops anyway. This means a formant-correction stage does **not** need to be perfect across many cascading generations to meaningfully address the complaint — it needs to be convincing on the first couple of passes, which is a materially smaller bar than "solve formant preservation for an infinitely-cascading signal in general."

**On latency and stability specifically** (expanded in §4): any of the block-based techniques in §1b/§1c need to accumulate a window of samples before computing an envelope, which is unavoidable added round-trip latency if that correction sits on the recirculating path (as it must, per the reasoning above and per the coordinator's own correct anticipation in the task brief). This project's own `SafetyLimiter` design rationale — quoted directly from `Source/DSP/ShimmerReverbEngine.h`'s comments — already establishes the precedent that **added latency inside this specific loop is treated as a serious structural cost, not a minor one**: a lookahead limiter was explicitly rejected in favor of a memoryless soft-knee shaper specifically because "a lookahead limiter's internal delay buffer would corrupt `DattorroTank`'s empirically-tuned delay-line round-trip timing." Any block-based envelope-correction stage is a strictly larger latency addition than a lookahead limiter's typical few-ms buffer, so this concern applies with at least as much force here. This is not merely analogous to the comb-filtering/stability tension `docs/fdn-shimmer-reverb-research.md`'s §3 already documented (direct feedback vs. a copy detoured through the shifter's own ~80ms internal buffer) — **adding a new, separate delay element (the envelope-analysis window) inside the same loop is the same class of problem, one level up**: it changes the effective round-trip length between the tank's direct path and the shifter's path yet again, meaning the already-hard-won `frozenMaxShimmerBlendWeight` sweep (0.85 → 0.01 at Freeze, found only by a careful non-monotonic search) cannot be assumed to still hold and would need to be re-derived from scratch against the new timing.

## 3. Feasibility: augment the existing WSOLA grain-pool, or replace it?

**Augmentation is technically possible in principle, but does not dodge the latency problem — it only relocates it.**

Concretely, against `Source/DSP/PitchShifter.h/.cpp`'s actual current design (grain pool of finite-lifetime `Grain`s, a shared `DelayLine<Lagrange3rd>`, a deterministic WSOLA `findAlignmentOffset()` correlation search, all operating **per-sample**, with no block buffering anywhere):

- **Option A — full replacement with an FFT/phase-vocoder core** (à la `stftPitchShift`/Signalsmith Stretch): this discards the grain pool, the WSOLA alignment search, and the per-sample `processSample()` contract entirely, replacing them with a block-accumulate-then-transform model. `ShimmerReverbEngine::process()`'s per-sample loop structure (`shifter.processSample(tank.peekFeedbackSignal())` called once per sample, immediately used to drive `tank.processSample()` the same sample) would need to become block-buffered on both sides, or the tank itself would need to accept delayed feedback — a structural change to the loop's timing model, not just a swap of one class's internals. This is the most disruptive option.
- **Option B — pitch-synchronous grain sizing (PSOLA/TDHS) inside the current per-sample grain-pool shape**: closer to a modification than a replacement (grains stay finite-lifetime, launched from a pool, read via the same shared delay line) — but it requires adding a real-time pitch/period detector to size and place each grain, which is new machinery this class has never needed (the current WSOLA search *aligns* grains for phase coherence but never needs to know the input's actual period). Per §2, this is the option most likely to reintroduce mistracking/glitching on this project's actual (non-monophonic, diffused) signal — the single biggest risk of the whole formant-preservation direction.
- **Option C — wrap a spectral-envelope correction stage (LPC or cepstral) *around* the existing grain-pool core, leaving it as the pitch engine**: this is the genuinely additive option. The grain pool keeps doing exactly what it does today (pitch-accurate, phase-aligned, per-sample shifting); a separate envelope-tracking side path computes a correction filter from (a) a short window of the signal *entering* the shifter and (b) a short window of the grain pool's own *output*, then applies that correction filter to the output before it re-enters the tank. This does **not** require discarding `PitchShifter`'s core mechanism — it requires adding a new block-based analysis component alongside it (most naturally implemented as an LPC estimator via Levinson-Durbin recursion, which is cheap, O(order²) per analysis frame, and real-time-safe with pre-sized buffers — no `processBlock`-time allocation, consistent with this project's hard rule). This is the only option that doesn't force a rewrite of the already-tuned, already-tested grain-pool mechanics — but it still requires an analysis window (see §4), so it does not avoid added latency, only minimizes it relative to Option A's full FFT frame sizes.

## 4. Latency and real-time-safety implications

| Approach | Minimum practical analysis window | Where the latency must live |
|---|---|---|
| Option A (FFT phase vocoder, full replacement) | 1024–2048 samples (~23–46ms at 44.1kHz) per Bernsee's own recommended frame sizes, often more in practice with high overlap factors | Necessarily inside the loop if the recirculating content is to be corrected (see below) |
| Option B (PSOLA/TDHS, pitch-synchronous grains) | One pitch period (~2–20ms depending on fundamental — shorter for higher notes, ironically longer exactly for the low notes this project doesn't have a complaint about) | Inside the loop, comparable order of magnitude to the current grain length, *if* period detection is reliable (§2's caveat) |
| Option C (LPC/cepstral envelope wrap, augmenting current grains) | Materially smaller than Option A — LPC analysis windows for envelope estimation are commonly 10–20ms in speech-processing practice (general DSP knowledge, not independently re-verified against a source specific to non-speech/reverb content in this research) | Inside the loop, smaller than Option A but still non-zero |
| Do nothing / accept trade-off | 0ms | N/A |

**Can correction move outside the loop instead — only on the final wet output?** This was investigated directly per the coordinator's question, and the answer is **no, this would not address the complaint**. Per §2 and per `docs/fdn-shimmer-reverb-research.md`'s own account of Phase 8, the audible shimmer character is carried predominantly by `tankOut` — the tank's own output, which already contains many generations of previously-recirculated, previously-diffused shifted content baked in via the branch A/B allpass chains over time. The shifter's raw output reaches the ear two ways: indirectly, via re-entering the tank and being heard later as part of `tankOut` (the dominant path), and directly, via the small, deliberately-de-emphasized `Width`/decorrelation difference term (`shimmerWidthGain * 0.5 * (safeFeedback - quadratureSafe)`, default weight 0.15). Correcting only that direct term, or only a final output tap, would leave the dominant `tankOut` path — and therefore the actual complaint — untouched. **Formant correction has to sit on the signal before it re-enters the tank's cross-feed to have any real effect on what's being described as "chipmunk," which means it cannot avoid living inside the loop's timing, confirming the latency-vs-loop-timing tension is unavoidable for any option that actually solves the stated problem.**

**Consequence for this project's already-tuned stability work**: any non-trivial added latency inside the loop changes the effective delay between the tank's own direct feedback (`feedbackFromB`) and the externally-shifted-and-now-also-envelope-corrected feedback (`externalFeedback`) — the exact two paths whose interference `docs/fdn-shimmer-reverb-research.md`'s §3 already identified as the mechanism behind the measured Freeze-decay comb-filtering bug. Changing that relative delay by even 10–20ms (Option C, the cheapest realistic option) is not a free parameter change — it plausibly moves where the destructive-interference nulls fall, meaning `frozenMaxShimmerBlendWeight`'s already-swept value (0.01f, found only via a careful non-monotonic search that a short test alone would have gotten wrong) cannot be assumed to remain valid and would need to be re-derived. This should be budgeted as real risk, not a footnote.

## 6. Concrete recommendation

**No option here is a clean, low-risk win — and it would be dishonest to present one as such.** Every technique found in the literature and in open-source practice was built and validated for one-shot processing of largely-monophonic material; none was built or tested for a signal that is diffuse, potentially polyphonic, and — critically — recirculating through its own correction repeatedly. Given that, ranked:

1. **Do not pursue Option A (full FFT/phase-vocoder replacement) as a first move.** Its latency (tens of ms) is large enough, relative to this project's own stated tolerance for latency inside this exact loop (`SafetyLimiter`'s design rationale), to force a restructuring of the loop's timing model and a full re-validation of the Freeze/stability tuning already built — a cost and risk profile comparable to (arguably worse than) the FDN-core rewrite `docs/fdn-shimmer-reverb-research.md` already recommended against, for a benefit (formant fidelity) that itself degrades on this project's actual non-monophonic, cascading signal.
2. **Do not pursue Option B (PSOLA/TDHS pitch-synchronous grains) as the primary mechanism.** Its single biggest requirement — reliable real-time period detection — is the worst match of any option to this project's actual signal (diffuse, potentially chordal, increasingly non-tonal across cascading generations), and risks reintroducing exactly the class of mistracking/glitching bug this project spent Phases 3 and 7 eliminating from the current design.
3. **If the owner wants to pursue formant preservation at all, Option C (a small LPC-based envelope-correction stage wrapped around the existing grain-pool core) is the only option that doesn't force discarding already-tuned, already-tested work.** It should be treated as its own scoped investigation, with the same empirical discipline this project has used throughout (a dedicated diagnostic test — analogous to the existing pitch-accuracy and spectral-sideband tests — measuring formant-frequency-ratio error before and after, plus a fresh Freeze-decay-dB measurement to catch any re-introduced comb-filtering from the new added latency) **before** committing to shipping it. Expect a multi-round tuning arc similar in shape to the Freeze investigation, not a drop-in fix.
4. **A cheap, zero-added-latency fallback worth naming explicitly**: a crude spectral-tilt compensation (a single shelving filter whose coefficients are keyed to the current pitch-shift ratio, correcting only the gross spectral-tilt component of the formant shift, not true formant positions) adds no new latency, no new failure mode, and is architecturally consistent with the loop's existing simple in-loop filters (`DCBlocker`, per-branch damping). This is **not** real formant preservation and will not fully fix the complaint, but it is the only option on this list that carries essentially none of §4's stability risk, and could be tried first as a cheap partial mitigation while a real Option C investigation is scoped.

**Implemented, 2026-08-23** (the owner chose this option over Option C): `Source/DSP/SpectralTiltCompensator.h`, a one-pole lowpass whose coefficient is linear in coefficient-space (not cutoff-Hz space, to guarantee an exact bit-identical passthrough at semitones<=0) between 0.0f at no shift and a REASONED target (~3kHz cutoff) at the full +24st extreme -- keyed to the shifter's EFFECTIVE (post-Freeze-crossfade) semitones, not the raw knob value. Applied to both the primary and quadrature shifted signals inside `ShimmerReverbEngine::process()`, immediately after the shift and before DC blocking, so it shapes exactly the signal re-entering the tank -- no new latency (a one-pole IIR needs no lookahead), so it did not require re-deriving `frozenMaxShimmerBlendWeight` or any other already-tuned stability constant, as this document's §4 anticipated a block-based option would. Full test suite green (0 regressions).

**Ear-tested, 2026-08-23 -- confirmed ineffective, and now understood WHY (not just "needs re-tuning").** User reported "still sounds chipmunk on the highest notes, no noticeable changes." Root cause, worked out after the fact: at the shipped settings the darkening only starts around ~8kHz (at the default +12st shift) -- nowhere near where a shifted HIGH note's fundamental actually lands (e.g. an 880Hz input shifted +12st lands at 1760Hz, well below 8kHz). Lowering the cutoff enough to actually reach that content runs into a hard wall: **for a high input note, the frequency range causing the "chipmunk" character is the SAME frequency range as the wanted shimmer effect itself.** A low note's shifted content moves up into a higher octave where a tilt filter can discriminate "excess brightness" from "the wanted shift" (plausibly why low notes sounded fine) -- a high note has no such separation, so a static lowpass can only choose between leaving chipmunk alone (as shipped) or muting the shimmer effect on high notes entirely (if pushed low enough to matter). **This is not a mistuning to fix with a different cutoff value -- it is the actual ceiling of what any single static filter (this crude approach's entire category) can do for this specific case.** The implementation stays in the codebase (it's a real, zero-cost, zero-regression stage -- see the comparison table in section 5 above, "essentially none of section 4's stability risk" still holds), but should not be expected to ever meaningfully fix the high-note case no matter how its constants are retuned.

**Decision, 2026-08-23**: owner has chosen to proceed with the **Option C investigation** (LPC-based spectral-envelope correction wrapped around the existing grain-pool core, ~13-21 dev days + open-ended ear-tuning tail per section 7 above) as the real fix, explicitly deferred to a future session ("we will go for it tomorrow's session"). **This is the next thing to pick up.** Before writing any code: re-read this document in full (especially sections 2-4's constraints: the recirculating-loop timing tension, the "correction must sit before the tank's cross-feed, not just on final output" finding, and the expectation that `frozenMaxShimmerBlendWeight` will likely need re-deriving once real added latency enters the loop), then scope Option C's first concrete step (most likely: a standalone LPC envelope-estimator prototype, tested in isolation before touching `ShimmerReverbEngine`/`DattorroTank` at all, per this project's established "measure before integrating" discipline).

## 7. Rough effort estimate (Option C: LPC-based envelope-correction augmentation)

**This is a rough, non-committal estimate for the recommended option only — not a plan.** Assumes keeping `PitchShifter`'s existing grain-pool core entirely intact and adding a new envelope-correction stage alongside it.

| Item | Relative size | Rough days | Notes |

| LPC envelope estimator implementation (Levinson-Durbin, windowing, order selection) | Medium | 2–3 | New subsystem; needs its own real-time-safety pass (pre-sized scratch buffers, no `processBlock`-time allocation) per this project's hard rule |
